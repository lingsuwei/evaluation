## 1. 背景与目标

onto-eval 当前为**单 Agent 单题评测**模型（`EvaluationTask.agent_id` 单值，`AgentRun` 单 Agent 单执行）。需新增**多 Agent 协作工作流评测**能力：支撑 agent_swarm 的 N-Agent 协作（首期 1 Leader + 2 Members = 3 Agent），输出：

- **结果评测**：对 Leader 的 `final_answer` 跑现有质量指标（correctness/faithfulness/answer_relevancy）。
- **过程评测**：按 member 切分协作轨迹，复用 DeepEval 单 Agent 过程指标（step_efficiency/plan_adherence/plan_quality）分别计算。
- **工作流对比**：版本/配置/Topology 对比（业界 Workflow Lift + 系统级对比 + 两层指标范式）。

### 1.1 核心约束

- **agent_swarm 尽量不动代码**：唯一突破点为 D1(c)——在 sync 端点补 `team_event`→Langfuse span 埋点（约 30~50 行），**不触碰协作编排逻辑**。
- **onto-eval 保证通用性**：核心抽象（WorkflowRun/AgentRole/CollaborationTrace）框架无关，agent_swarm 是首个 Provider。

## 3. 设计原则（与 [设计范式.md](./设计范式.md) 一致）

1. **复用优先**：RunSpanNode 树已是协作轨迹载体；Operation Registry 已是 eval-owned 打点；Span 树 Diff 已是结构对比。新增只做"语义层"，不动物化层热路径。
2. **agent_swarm 最小侵入**：只补一处 Langfuse 埋点（D1c），不要求实现 onto-eval 专属契约。
3. **核心抽象通用**：WorkflowRun / AgentRole / CollaborationTrace 框架无关，接新框架只换 Adapter。
4. **过程评测不阻塞结果评测**：trace 物化异步，结果分照常先出（§4.5 SLO：P95 < 60s）。
5. **不破坏评测/观测解耦**（回应 §19 风险）：role_roster 属运行时观测事实，非评测语义；过程评测仍走 run_span_nodes + checkpoint，不另起评测域。
6. **不重复造轮子**：与 SwarmBench 互补而非替代；不复用其质量不达标的指标。

## 4. 核心架构决策：D1(c) 如何解锁现有物化管线

### 4.1 阻断点

[agent_swarm 的 `run_sync_inference`](file:///d:/work/HT%E9%9B%86%E5%9B%A2/soft/agent_swarm/backend/routes/chat.py) 事件循环只处理 8 类事件（token/reasoning/usage/tool_call/tool_result/answer/confirmation_required/error/done）。Team 模式下 Members 的协作活动走 `team_event`，**该类型未被处理**，因此 Langfuse trace 里只有 Leader 的 LLM/工具调用，Members 的任务认领/消息传递**不可见**。

### 4.2 D1(c) 补丁（agent_swarm 侧，最小改动）

在 `run_sync_inference` 事件循环增加 `team_event` 分支：当收到 team_event（含 member_name、event、payload）时，调用已有 [LangfuseTracer](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/agent_swarm/backend/evaluation/langfuse_trace.py) 创建嵌套子 span：

```
trace 根 (agent_swarm workflow)
 └─ Leader agent_turn (已有)
     ├─ Leader llm generation (已有)
     ├─ Leader tool: create_task (已有→补 member 归因)
     ├─ Member[analyzer] agent_turn (新增, attributes.agent.member.name="analyzer")
     │   ├─ Member llm generation (新增)
     │   └─ Member tool: claim_task / send_message (新增)
     └─ Member[executor] agent_turn (新增, attributes.agent.member.name="executor")
         └─ ...
```

每个新增 span 写入 OTel 属性（与 [agent-otel-joint-spec.md](./agent-otel-joint-spec.md) 对齐并扩展）：

| Attribute | 写入方 | 说明 |
|-----------|--------|------|
| `agent.member.name` | agent_swarm（D1c 补丁） | Member 身份，如 analyzer/executor |
| `agent.role` | agent_swarm | leader / member |
| `agent.step.kind` | agent_swarm | 扩展枚举：`llm`/`tool`/`router`/`team_tool` |
| `agent.tool.name` | agent_swarm | create_task / claim_task / send_message / update_task |

> LangfuseTracer 已有 `start_agent_turn(name, metadata)` / `start_tool_span(tool_name, run_id, args)`，只需在 team_event 分支调用并传 member_name。改动约 30~50 行，不触碰 `team_runtime_service.py`/`team_config.py`/openjiuwen。

### 4.3 onto-eval 侧：现有物化管线零改动吃下协作轨迹

补丁完成后，onto-eval 的**唯一物化路径完全复用**（§7.5.2）：

```
agent_swarm sync 端点 → Langfuse SDK 写完整 trace（含 Member 子 span）
onto-eval internal_sync Worker → 拉 Langfuse trace（不变，§7.5.2 唯一路径）
Runtime Fact Builder → run_span_nodes 物化为树（不变，member span 自然成子节点）
Trace Adapter → 归一化 attributes（扩展识别 agent.member.name）
Operation Registry → 后置打 eval.operation.id（扩展 team 操作规则）
```

**这是选 D1(c) 的根本收益**：onto-eval 不需要新建 SSE 流式适配器、不耦合 agent_swarm 文件系统、过程评测覆盖完整。

## 5. 领域模型扩展（精简版，复用优先）

### 5.1 SUT 侧：`agents` 表新增 `agent_kind`

最小改动复用现有 Agent/版本模型，避免新顶层实体：

| 改动 | 说明 |
|------|------|
| `agents` 表新增 `agent_kind` 列（枚举 `single`/`workflow`，默认 `single`，加索引） | agent_swarm 注册为 kind=workflow 的一个 Agent（logical_agent_id=agent_swarm，可多版本）。查询 discriminator，支持过滤。需 Alembic 迁移 |
| `orchestration_pattern` 放入 `agents.inference_config` JSON | `supervisor_predefined`/`hierarchical`/`sequential`/`dag`（agent_swarm=supervisor_predefined，可观测不强校验） |

> 不新增 WorkflowAgent 顶层表——workflow 只是一种 Agent kind，复用版本治理、注册预检、资产同步全链路。

### 5.2 运行侧：role_roster 借 `agent_snapshot`，不新增列（C2 简化）

`agent_runs` 已有 [`agent_snapshot` JSON（≤8KB）](./onto-eval评测优化架构设计说明书.md) 专存"运行时 Agent 配置快照"。role_roster 本质即运行时配置，**借 agent_snapshot 扩展**，不在 agent_runs 加列：

```json
// agent_snapshot 扩展结构
{
  "agent_id": "ag_xxx",
  "logical_agent_id": "la_xxx",
  "agent_version": "1.2.0",
  "agent_name": "agent_swarm",
  "agent_kind": "workflow",
  "inference_config_hash": "sha256:...",
  "model": "gpt-4o",
  "workflow": {
    "orchestration_pattern": "supervisor_predefined",
    "member_count": 3,
    "role_roster": [
      {"role": "leader", "member_name": "main", "persona": "..."},
      {"role": "member", "member_name": "analyzer", "persona": "..."},
      {"role": "member", "member_name": "executor", "persona": "..."}
    ]
  }
}
```

- role_roster 由 Runtime Fact Builder 在物化完成后从 span 树 `agent.member.name` 去重回填（I6：onto-eval 只读不配）。
- `agent_runs` 仅靠 `agent_snapshot` 承载工作流语义，**零新列**，单 Agent 运行的 snapshot 不含 `workflow` 段。

### 5.3 Span 层：RunSpanNode 成员归因（无 schema 改动）

[RunSpanNode.attributes](./onto-eval评测优化架构设计说明书.md) 是 JSONB 字典，直接扩展属性命名空间（§8.8.2 `agent.*` 前缀范式）：

| Attribute | 写入方 | 说明 |
|-----------|--------|------|
| `agent.member.name` | agent_swarm（D1c） | Member 身份 |
| `agent.role` | agent_swarm | leader / member |
| `agent.step.kind` | agent_swarm | 扩展 `team_tool` |
| `eval.operation.id` | onto-eval Trace Adapter（后置） | team 操作归一，如 `team.claim_task`/`team.send_message` |

**关键**：`agent.logical_agent_id`（现语义=同族多版本）**不复用**为 member 标识，避免语义冲突；新增独立 `agent.member.name`。

### 5.4 通用三件套抽象（D2a，落地为约定而非大表）

| 抽象 | 落地方式 | 框架无关性 |
|------|---------|-----------|
| **WorkflowRun** | `agent_runs` 中 kind=workflow 的行 + agent_snapshot.workflow | 任意框架一次工作流执行 = 一行 |
| **AgentRole** | agent_snapshot.workflow.role_roster 内对象 | 任意框架角色清单统一表达 |
| **CollaborationTrace** | RunSpanNode 树 + `agent.member.name` 归因 | 任意框架把成员活动写成嵌套 span 即可复用 |

> 接 langgraph 时：langgraph messages/threads → Adapter 转成带 `agent.member.name` 的嵌套 span → 物化管线不变。即 D2(a) 通用性所在。

### 5.5 OTel 联合规范合规与适配策略

#### 5.5.1 合规现状

[agent-otel-joint-spec.md](./agent-otel-joint-spec.md)（M-03）规定 Langfuse observation.metadata 须写 `agent.*` 键。核验 agent_swarm [LangfuseTracer](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/agent_swarm/backend/evaluation/langfuse_trace.py)：**全套 `agent.*` 属性零写入**——结构信息全在 observation `name`（如 `llm_reasoning:{N}`、`{tool_name}`）与 input/output，metadata 仅含业务键（`trial_id`/`scenario_id`/`category`/`onto_eval_run_id`）。onto-eval [trace_adapter](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/onto-eval/backend/services/trace_adapter.py) 对 agent_swarm 观测**全部降级为 `legacy:{type}:{name}` 聚合键**（标记"规则易碎"）。

#### 5.5.2 要求合理性分类（spec 必选 vs onto-agent 私有）

spec 实际**必选**仅 `agent.step.id` + `agent.step.kind`；**推荐** `agent.tool.name`/`agent.logical_agent_id`/`agent.version`。用户列的 5 条是 onto-agent 实现的细化，需区分性质：

| # | 要求 | 性质 | agent_swarm 现状 | 处置 |
|---|------|------|----------------|------|
| 1 | TOOL: `agent.tool.name`/`step.kind=tool`/`step.id=tool:{name}`/`tool.call_index` | spec 推荐（OTel 最佳实践） | ❌ name 字段有工具名，metadata 仅 `{category:skill}` | **onto-eval 适配器映射**（见 5.5.3-B） |
| 2 | GENERATION: `step.kind=llm`/`step.id=llm:main_iteration` | spec 必选 | ❌ generation 无 metadata，name=`llm_reasoning:{N}` | **onto-eval 适配器映射** |
| 2b | `llm:reasoning_summary` 角色 | **onto-agent 私有** | N/A | agent_swarm 将 reasoning token 混入主 generation（[chat.py](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/agent_swarm/backend/routes/chat.py) `append_llm_token`），无独立 reasoning_summary generation，**不适用** |
| 3 | router span 容器 `tools:main_iteration_*` | **onto-agent 私有架构** | ❌ 扁平结构无容器 span | onto-eval 适配器按 generation round 推导 `agent.iteration`，**不合成 router 容器**（接受 agent_swarm 扁平拓扑为原生结构） |
| 4 | trace 根 `agent.logical_agent_id`/`agent.version` | spec 推荐（OTel Resource） | ❌ **不满足**：此 2 字段是 **onto-eval 评测侧 taxonomy**，agent_swarm 无原生概念；onto-eval `_inject_eval_sync_context`（[inference_service.py L229](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/onto-eval/backend/services/inference_service.py#L229)）已把值放进请求 `context` 发出，但 agent_swarm `run_sync_inference` 只转发了 `agent_run_id`/`langfuse_project`，**忽略了这 2 个**（[chat.py L54-57](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/agent_swarm/backend/routes/chat.py#L54)） | **agent_swarm D1c 转发**（推荐，见 5.5.3-A2）：trace 根 metadata 加 `agent.logical_agent_id`/`agent.version` 从 context 读，~2 行，trace 自描述、双方识别；备选 onto-eval 物化时从 AgentRun 表注入（trace 非自描述） |
| 5 | `execute_script`: `agent.script.path` | **onto-agent 私有工具** | N/A | agent_swarm 无 `execute_script` 工具（其等价物为 `execute_shell_command`/`execute_python_code`），**不适用**；可选对等写 `agent.command.text`（非必须） |

#### 5.5.3 分层适配策略（关键：agent_swarm 现有行为零改动）

把"新增 span"与"存量观测"分开处置，贯彻"agent_swarm 尽量不动代码"原则：

**A. 净新增 team_event member spans（D1c 补丁）**——agent_swarm 侧写全套 `agent.*`
Member 协作 span 是 net-new（不写就不存在），从第一行起即遵循规范：写 `agent.member.name`/`agent.role`/`agent.step.kind=team_tool`/`agent.tool.name`/`agent.step.id=tool:{name}`/`agent.tool.call_index`。这是 D1c 补丁的一部分。

**A2. trace 根 logical_agent_id/version（D1c 补丁，~2 行）**
此 2 字段是 onto-eval 评测侧 taxonomy，agent_swarm 无原生概念，但 onto-eval 已在请求 `context` 里发送（[`_inject_eval_sync_context`](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/onto-eval/backend/services/inference_service.py#L201)）。agent_swarm [`run_sync_inference`](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/agent_swarm/backend/routes/chat.py#L54)（L54-57）现只转发 `agent_run_id`/`langfuse_project`，需补 2 键从 `context` 读 `logical_agent_id`/`agent_version` 写入 trace 根 metadata（键名用 `agent.logical_agent_id`/`agent.version`，spec 范式）。代价 ~2 行，折叠进 D1c。trace 根自此自描述，[`normalize_observation_attributes`](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2%E5%9B%A2/soft/onto-eval/backend/services/otel_attributes.py#L18) 的 metadata-copy 直接命中，无需走顶层字段映射分支。

**B. 存量 Leader 观测（tool/generation）**——onto-eval 适配器侧映射，agent_swarm 不动
实现 spec §7.3 规划的 `otel_attribute_mapping.yaml`：把 agent_swarm observation `name` + 现有 metadata 键映射为 `agent.*` 属性，在 [trace_adapter.py](file:///d:/work/HT%E9%9B%86%E5%9B%A2%E5%9B%A2/soft/onto-eval/backend/services/trace_adapter.py) `normalize_observation_attributes` 后置注入：

```yaml
# otel_attribute_mapping.yaml（agent_swarm Provider 段）
provider: agent_swarm
rules:
  - when: { as_type: tool }
    set:
      agent.step.kind: tool
      agent.tool.name: "${observation.name}"
      agent.step.id: "tool:${observation.name}"
      agent.tool.call_index: "${sibling_order_among_tools}"
  - when: { as_type: generation, name_regex: "^llm_reasoning:(\\d+)$" }
    set:
      agent.step.kind: llm
      agent.step.id: "llm:main_iteration"
      agent.iteration: "${regex.group(1)}"
```

- 映射后 `derive_aggregate_key` 走 `agent.step.id` 正常路径，告别 `legacy:` 回退。
- `agent.logical_agent_id`/`agent.version`（要求4）：由 A2（agent_swarm D1c 转发 context）处理，**不进 mapping**。备选（若 agent_swarm 不改）：mapping 引擎物化时从 `AgentRun` 上下文补注入到 span——但 trace 非自描述，不推荐。
- **注意**：`otel_attribute_mapping.yaml` 引擎是**新建项**（spec §7.3 标"规划"，代码未实现）；现成的只有消费者侧 `normalize_observation_attributes`/`derive_aggregate_key`/`inject_eval_operation_ids`。M-W2 含此新建。
- router 容器（要求3）不合成——agent_swarm 扁平拓扑作为其原生结构登记，Span 树 Diff 按实际扁平树对比。

**C. 不适用项**：要求 2b/3-router/5 标记为 onto-agent 私有，对 agent_swarm 不适用，映射表不强制。

#### 5.5.4 结论

- spec 必选（`agent.step.id`/`agent.step.kind`）+ 推荐（`agent.tool.name`）→ **全部由 onto-eval 适配器侧满足**（mapping + AgentRun 注入），agent_swarm 现有 Leader 观测**零改动**。
- 净新增 Member span → agent_swarm D1c 补丁直接写规范属性。
- onto-agent 私有约定（2b/3-router/5）→ 标记不适用，不强加。
- 通用性：`otel_attribute_mapping.yaml` 是 Provider 级配置，接 langgraph 时另写一段 mapping，物化层不变——契合 D2(a)。

## 6. agent_swarm 侧改动清单（D1c，最小）

## 9. 与 SwarmBench 互补并存（D4→a）

基于 SwarmBench 质量评估（占位符多、协作覆盖低、数据契约不兼容），明确分工：

| 评测域 | 归属 | 评什么 |
|--------|------|--------|

| 推理答案质量 | **onto-eval** | correctness/faithfulness/answer_relevancy on final_answer |
| 版本/配置对比 | **onto-eval** | Workflow Lift + role_roster diff + Span 树 Diff |

> 两者运行模式天然分离：SwarmBench 跑仿真 Trial（场景驱动），onto-eval 调 sync 端点（QA 驱动）。onto-eval **不 import agent_swarm 评测模块**，零耦合。
